## 行动 1：确认能从哪里拿到真实对话数据

**日期**：2026-10-06

**做了什么**
检查本地开发环境里有没有可分析的真实对话。

**为什么**
第 1 步要用真实用户的消息来决定做什么、出考题。先确认数据在哪，避免基于假数据做判断。

**怎么做的**
1. 查看 `apps/api/.env` 里配置了哪些变量（只看变量名，不看值）：只有 OCR 相关的三个，**没有 `DATABASE_URL`，也没有 AI 密钥**。
2. 查看 `apps/api/src/config.ts` 和 `apps/api/src/ai/assistant.ts`：没有数据库地址时，后端用本地文件 `apps/api/.offerflow-data/state.json` 存数据；没有 AI 密钥时，用 `DemoAssistantProvider`，也就是**按关键词返回写死的演示回复**，根本不调用模型。
3. 统计本地文件里的消息：只有 15 条，都是开发时的测试数据。

**学到的概念**
- **环境变量（.env）**：同一份代码，在本地和生产环境连接不同的数据库、使用不同的密钥，靠的就是环境变量。`.env` 文件不提交到 git，因为里面有密码。
- **Provider 模式**：代码里先定义一个“能生成回答的东西”的接口，再提供两种实现：真模型版、演示版。根据有没有密钥决定用哪个。以后接入 agent、换模型，也是在这一层替换。

**结果**
真实对话只在生产数据库里，需要你导出。导出 SQL：

```sql
\copy (SELECT m.conversation_id, to_char(m.created_at AT TIME ZONE 'Asia/Shanghai', 'YYYY-MM-DD HH24:MI') AS sent_at, left(m.content, 500) AS user_message, jsonb_array_length(m.attachments) AS attachment_count, a.status AS reply_status, a.payload->>'feedback' AS feedback, left(a.content, 300) AS reply_preview FROM messages m JOIN users u ON u.id = m.user_id LEFT JOIN LATERAL (SELECT r.status, r.payload, r.content FROM messages r WHERE r.conversation_id = m.conversation_id AND r.role = 'assistant' AND r.created_at > m.created_at ORDER BY r.created_at LIMIT 1) a ON true WHERE m.role = 'user' AND u.deleted_at IS NULL AND u.email <> 'demo@offerflow.cn' AND m.created_at >= now() - interval '60 days' ORDER BY m.created_at DESC) TO 'chat-export.csv' WITH CSV HEADER
```

- 写法依据：`apps/api/src/store/postgres-store.ts` 里 admin 统计的真实查询。点赞点踩存在 `messages.payload` 的 `feedback` 字段；体验账号 `demo@offerflow.cn` 要排除。
- `\copy` 是 psql 的命令，必须写在一行里。
- 导出的文件放进项目根目录的 `.tmp/`（已被 git 忽略），用完删除。

## 行动 2：读懂现有的简历定制流程

**日期**：2026-10-06

**做了什么**
通读 `apps/api/src/ai/resume-tailor.ts`（241 行），弄清楚“AI 岗位定制”按钮按下去之后发生了什么。

**为什么**
第 2 步要给现有系统打基线分数，得先知道它是怎么工作的、哪里可能出问题。

**怎么做的（流程拆解）**

```text
用户在简历工作室点“AI 岗位定制”
  → 把简历整理成“结构化证据”：个人总结、技能、每段经历拆成带 id 的小块
  → 一次性发给 DeepSeek，附带 6 条规则（第 188～202 行），要求只返回 JSON
  → 模型返回“修改补丁”：哪个块改成什么、为什么改
  → 代码校验补丁（applyResumePatch，第 82～174 行）：
       · 块 id 必须是原来就有的
       · 改写后的字数必须在原文的 90%～110% 之间，否则整段丢弃
  → 前端展示“AI 建议修改 N 处”，用户确认后存为新版本
```

**关键发现**
1. **这是“单次 LLM 调用”，不是 agent**：一问一答，中间没有任何决策或循环。
2. **防编造只靠提示词**：第 6 条规则写着“数字、公司、学校、项目、日期、技术名和所有权强度均是锁定事实，不得新增或篡改”，但代码只校验结构和字数，**不检查模型到底有没有新增数字或技术名**。模型如果不听话，编造的内容会直接展示给用户。
3. **字数限制在 90%～110%，等于只允许换措辞**：这正是学生简历的痛点所在。素材单薄的简历，光改措辞改不好，需要追问用户、补充真实素材，这是 agent 才能做的事。

**学到的概念**
- **结构化输出（JSON mode）**：`response_format: { type: "json_object" }` 要求模型只返回 JSON，代码才能可靠地解析。
- **护栏要写在代码里，不能只写在提示词里**：提示词是“请求”，代码校验才是“保证”。模型大多数时候会听话，但“大多数时候”不够。
- **temperature**：控制模型输出的随机程度。这里设为 0.2，偏稳定。

**结果**
找到了第一个值得评测、也值得加固的点：编造检测。

## 行动 3：做第一个评分零件——编造检测器

**日期**：2026-10-06

**做了什么**
写了一个函数：给它“改写后的文字”和“证据”（原简历，以后还包括用户在追问中的回答），它找出改写后的文字里**在证据中找不到出处的事实**。

- 代码：`apps/api/evals/graders/fabrication.ts`
- 测试：`apps/api/tests/eval-fabrication.test.mjs`

**为什么**
- 演示主线的卖点是“新增的事实都能追溯到用户原话”，必须有工具证明这一点。
- 讲解文档第 6 节说过：**能用代码判断的，绝不用 LLM 评委**。代码判断零成本、百分之百稳定，应该最先做。
- 它不依赖生产数据，可以在等数据的时候先做。

**怎么做的**
只检查三类用代码能客观判断的事实：

| 类型 | 怎么判断 | 例子 |
|---|---|---|
| 数字 | 提取所有数字，看证据里有没有同样的数 | 原文没有“30”，改写后出现“提升 30%” → 疑似编造 |
| 英文技术名 | 提取英文词（不区分大小写），看证据里有没有 | 原文只有 Python、SQL，改写后多了 Tableau → 疑似编造 |
| 所有权升级 | 改写后出现“负责、主导、牵头、带领、独立完成”等词，但证据里没有 | 原文“参与调研”，改写成“主导调研” → 疑似编造 |

另外两个设计：
- **用户的回答也算证据**：以后 agent 追问时用户说“上线两周有 400 人注册”，改写里出现 400 就是合法的。这就是“可追溯”的实现基础。
- **允许清单**：目标岗位名（比如“AI 产品经理”）可以出现在个人总结里，不算编造。

最后汇总成一个指标：**编造率 = 含疑似编造的修改条数 ÷ 总修改条数**，目标是 0。

**已知的盲区**（写在代码开头的注释里）
- 中文数字（“三个”）识别不了
- 数字相同但单位换了（“30 人”改成“30%”）发现不了
- 中文的公司名、项目名没有检查（这些在现有结构里本来就不允许修改）

盲区交给后面的 LLM 评委和人工抽查来补。**一个评分工具不需要完美，但要清楚自己的边界。**

**学到的概念**
- **Grader（评分器）**：评测体系里负责“打分”的零件。一份考卷可以组合多个评分器：代码断言、LLM 评委、人工。
- **确定性（deterministic）**：同样的输入永远得到同样的结果。代码评分器是确定性的，LLM 评委不是。
- **单元测试**：用几个精心设计的小例子证明函数行为正确。这里 7 个测试分别覆盖：正常改写不误报、新增数字、新增工具、所有权升级、用户回答算证据、允许清单、汇总指标。

**结果**
- 7 个测试全部通过。
- 跑了整个 API 测试套件：72 个全部通过，新文件没有影响原有功能。这个动作叫**回归测试**：改了东西之后，确认原来好的地方没被弄坏。

**你可以自己试**
```powershell
cd apps/api
node --experimental-transform-types --test tests/eval-fabrication.test.mjs
```
然后打开测试文件，把某个例子里的数字改掉，再跑一次，看它怎么报错。这是理解代码最快的办法。

## 行动 4：从生产数据库只读导出真实对话

**日期**：2026-10-06

**做了什么**
经你同意后，通过 SSH 连上生产服务器，把最近 60 天的用户消息导出到本机的 `.tmp/chat-export.csv`。

**为什么这样做（生产环境的操作习惯）**
- **最小权限**：服务器上有两个数据库账号：做迁移的高权限账号 `MIGRATION_DATABASE_URL`，和 API 运行时用的低权限账号 `DATABASE_URL`。只是读数据，就用低权限的那个。万一命令写错，它也没有权限删表。
- **不打印密码**：检查环境变量时，只打印变量名，不打印值。
- **服务器上不留文件**：用 `COPY ... TO STDOUT` 让结果直接通过 SSH 流回本机，而不是先在服务器上生成文件再下载。少一个忘了删的敏感文件。
- **只读**：整个过程只执行了一条 `SELECT`。
- **先看统计，不看正文**：导出后先只看行数和列名，确认没问题再分析内容。

**怎么做的**
```bash
ssh offerflow-prod 'bash -s' > .tmp/chat-export.csv <<'REMOTE'
DBURL=$(grep -E '^DATABASE_URL=' /etc/jobkoi-api.env | cut -d= -f2-)
psql "$DBURL" -c "COPY ( 行动 1 里的 SELECT ) TO STDOUT WITH CSV HEADER"
REMOTE
```

**学到的概念**
- **SSH**：加密登录远程服务器的方式。你电脑上的 `~/.ssh/config` 给生产服务器起了别名 `offerflow-prod`，并指定了登录用的密钥文件。
- **最小权限原则**：每个操作只用完成它所需的最低权限，这是生产安全的第一原则。
- **CSV**：最通用的表格数据格式，Excel 能直接打开。

**结果**
808 条用户消息，来自 328 个对话，时间范围 2026-08-26 至 2026-10-06（41 天）。

⚠️ **隐私提醒**：这个文件含有用户的简历片段、姓名和手机号。考卷里的例子会全部改写和匿名化。**全部分析完成后，请删除 `.tmp/chat-export.csv` 和 `.tmp/chat-unique.txt`。**

## 行动 5：分析 808 条真实消息，确定演示主线

**日期**：2026-10-06

**做了什么**
逐条读完去重后的 631 条消息，再用关键词规则做定量分类，统计每类的占比和对话深度，并找出几类关键信号。

**为什么**
第 1 步的目的：用真实数据决定做什么，给作品找到“问题有多真实”的证据，也为考卷准备素材。

**怎么做的**
1. **去重**：首页快捷卡片会产生大量一模一样的消息，去重后便于阅读。
2. **人工通读**：先读一遍全部内容，形成定性判断。这一步不能省，关键词规则会漏掉很多语义。
3. **关键词分类**：每条消息按规则归入一类，规则有先后顺序（先判断“产品使用问题”，再判断“简历”，最后判断“找岗位”），算出占比。
4. **信号统计**：用关键词数出几类特别有价值的行为，比如“以为它在后台干活”。

**定量结果**

| 类别 | 消息数 | 占比 | 以此开头的对话 | 平均每个对话的消息数 |
|---|---|---|---|---|
| 找岗位 | 286 | 35.4% | 185 | 2.0 |
| 补充信息、短追问（如“27届”“全国都行”） | 198 | 24.5% | — | — |
| 简历 | 140 | 17.3% | 54 | **3.4** |
| 其他（多为直接粘贴的简历或 JD 长文本） | 66 | 8.2% | 5 | **8.2** |
| 产品使用、上传问题 | 39 | 4.8% | 14 | 3.7 |
| 面试 | 29 | 3.6% | 18 | 3.6 |
| 规划、咨询 | 26 | 3.2% | 22 | 1.7 |
| 闲聊、问是什么模型 | 19 | 2.4% | 17 | 2.5 |

**五个关键发现**

1. **找岗位量最大，但最浅，而且常常推荐错。** 平均每个对话只有 2 条消息，用户问完就走。典型抱怨：“可这都不是新疆的”“都不是化工方向的”“这些都是 27 届的岗啊”“我是想干外贸销售，你推送的什么”。8 条点踩里大部分来自找岗位。

2. **简历量第二，但最深。** 以简历开头的对话平均 3.4 条消息；直接粘贴长文本的对话平均 8.2 条。有用户围绕同一段实习经历来回改了二三十轮。反馈集中在语气和真实度：“太 ai”“太口语化”“不要太夸张”“要有量化结果”。

3. **用户会自然地补充真实素材，这正是“追问挖素材”的现成证据。** 被问到细节时，用户会主动给出真实数字：“一个班三十个人，大概两组，一组三个人获得”“当时做了三个浮标的数据，一个浮标大概 3k 条记录”“家装节阅读 1.4 万、520 活动阅读 2.4 万”。**现在的系统没有主动追问，是用户自己补的。**

4. **用户在给模型施加编造压力。** 原话：“你自己换算出最真实的数据吧，要求不要让面试官看出来造假”“你帮我编一个吧，我实在想不起来”。这说明编造检测器不是锦上添花，而是刚需：agent 要能拒绝编造，同时用追问帮用户找出真实的数字。

5. **用户已经把它当 agent 用了，但它做不到。**
   - **以为它在后台干活（11 条）**：“清单到了吗？”“结果出来了吗？”“进度如何”“等是我明天再按这个流程搜一次，还是你好了会主动联系我”
   - **要求代做操作（10 条）**：“你可以帮我投简历吗”“帮我填写网申简历”“你能不能直接把这些信息输到咱们这个软件的简历中心”“结合我的投递记录，推荐 3 个我还没投但匹配的岗”

**顺带发现的产品问题**（和 agent 无关，但值得修）
- 首页“找岗位”快捷卡片被点了 145 次，其中 **90 次（62%）用户没替换【岗位方向】这些括号就直接发了出去**。填空模板是失败的设计。
- 附件和 PDF 失败相关的消息有 7 条：“为什么给你发不了 PDF”“PDF 解析失败是啥意思”。
- 40 条回复被用户中途停止；点踩 8 条，**点赞 0 条**。可能是点赞按钮不够显眼，也可能是确实没有让人满意的回答。

**学到的概念**
- **定性 + 定量**：先通读（定性）找到“有哪些类型、用户怎么说”，再写规则统计（定量）得到“各占多少”。只做定量会漏掉语义，只做定性没有说服力。
- **频率 vs 深度**：一类需求出现得多，不代表它最有价值。找岗位频率最高，但用户浅尝辄止；简历频率第二，用户却愿意投入几十轮对话。选主线要两者都看。
- **用户行为是最好的需求文档**：“以为它在后台干活”这种行为，比任何问卷都更能证明用户需要 agent。

**结论：数据支持“以简历为核心”的演示主线**
- 简历是用户投入最深的场景，而且三个痛点（素材单薄、编造压力、语气反复修改）都是“追问挖素材 + 可追溯改写”能直接解决的。
- 找岗位作为入口：频率最高，但必须解决“推荐不对”的问题，否则演示第一步就会翻车。
- 用户已经在要求 agent 能力（代做操作、后台干活），这是作品故事里“为什么要做 agent”的最有力证据。

## 行动 6：建立简历定制考卷（10 道题）

**日期**：2026-10-06

**做了什么**
新建 `apps/api/evals/datasets/resume-tailor.json`，包含 10 道“简历 + 目标岗位”的考题。

**为什么**
要给现有的简历定制打基线分，得先有一份固定的考卷。考卷固定下来，以后每次改动都用它重考，分数才有可比性。

**怎么做的**
- **人物原型来自真实数据，内容全部虚构**：行动 5 里看到的 10 类典型求职者（汉语言文学投行政、会计转运营、电商直播、博士投药理……），每类写一个虚构人物，换掉所有真实姓名、学校、公司和联系方式，经历改写成相似但不相同的内容。
- **每道题包含四部分**：
  - `job`：目标岗位（公司、职位、职责、要求）
  - `resume`：候选人简历（总结、技能、经历）
  - `keywords`：JD 里**候选人确实有相关经历**、改写后应该被突出的能力词
  - `archetype`：一句话说明这题考的是哪类用户
- **刻意保留真实简历的毛病**：经历写得口语化（“学院有活动时去拍照，写新闻稿”）、动作模糊、缺少量化。这样才考得出定制能力。

**学到的概念**
- **数据集（dataset）**：一组固定的输入和期望，是评测的基础。
- **匿名化**：用真实数据的“模式”，不用真实数据的“内容”。这样考卷能贴近真实用户，又不泄露隐私，还能放心提交到 git。
- **代表性**：10 道题覆盖不同专业、不同岗位、不同的简历毛病，而不是 10 道相似的题。考卷的代表性决定了分数能不能反映真实表现。

## 行动 7：写基线脚本，先跑一遍冒烟测试

**日期**：2026-10-06

**做了什么**
新建 `apps/api/evals/run-resume-tailor.ts`：读取考卷，对每道题调用**现有的** `createResumeTailorProvider`，用编造检测器打分，汇总成报告并保存到 `apps/api/evals/results/`。

## 行动 8：发现并修正评分器的误报

**日期**：2026-10-06

**做了什么**
冒烟测试里唯一一条“疑似编造”是：原文“运营 60 余个热点事件，**做**内容解读”，改写成“**负责**内容解读”。检测器报了“所有权升级”。

我判断这是**误报**：原文本来就是本人在做，“做”换成“负责”不算夸大。真正要抓的是“参与 → 主导”这种把配角写成主角的情况。

**怎么修的**
修改 `apps/api/evals/graders/fabrication.ts`：只有当**这一条修改的原文**里有“参与、协助、配合、辅助、帮忙、帮助、支持”这类弱动词，改写后却出现“负责、主导、牵头”等强动词时，才算所有权升级。并补了两个测试：

- “做 → 负责”：不报警
- “参与 → 负责”：仍然报警

测试从 7 个增加到 9 个，全部通过。

**学到的概念**
- **评分器也需要被评测**：误报（把对的判成错）和漏报（把错的判成对）都会让分数失真。每次评分器报错，都要人工看一眼，判断是模型的问题还是评分器的问题。
- **精确率（precision）和召回率（recall）**：精确率是“报警的里面有多少是真问题”，召回率是“真问题里有多少被报出来”。这次修改提高了精确率，代价是可能漏掉少数“做 → 主导”式的夸大。这个取舍是有意的，已经写在代码注释里。
- **用测试锁住行为**：修完 bug 就加一个测试，以后谁改坏了，测试会立刻报错。

## 行动 9：诊断为什么“一处都没改”（以及一个被推翻的猜测）

**日期**：2026-10-06

**做了什么**
写了诊断脚本 `apps/api/evals/diagnose-resume-tailor.ts`。它截获模型的原始回复，和代码最终采纳的修改做对比，看修改建议在哪一步消失了。

**过程（包括我犯的错）**
1. **第一个猜测**：修改被“字数必须在原文 90%～110%”这条规则丢弃了。第一版诊断显示很多条目“被丢弃”，但其中大部分字数正好是原文的 100%，这与猜测矛盾。
2. **第二个猜测**：模型返回的块 id 和原 id 对不上，修改被静默跳过。我把发给模型的块 id 和模型返回的原始 JSON 打印出来对比，**id 完全对得上，这个猜测被推翻了**。
3. **真正的原因**：在同一份原始回复里看到，模型返回的文字**和原文一模一样**。比如“参与 2 家企业的年报审计，负责底稿整理和凭证抽查”，原样还了回来。代码发现前后一样，就不算修改。
4. 修正诊断脚本，把“原样返回”和“超字数被丢弃”分开统计。

**结果**

| 去向 | 数量 | 占比 |
|---|---|---|
| 模型原样返回原文 | 21 | 58% |
| 被字数规则丢弃（改写后达到原文的 110%～137%） | 6 | 17% |
| 真正生效 | 约 9 | 约 25% |
| 合计（模型返回的修改） | 36 | 100% |

**为什么会这样**
提示词同时要求“不能新增任何事实”和“字数保持在 90%～110%”。对素材本来就单薄的学生简历，模型能做的只剩换几个词；稍微展开一点，又会被字数规则丢掉。**它不是没尽力，而是被规则困住了。**这正是 agent“追问挖素材”要解决的问题：有了用户补充的真实素材，才有东西可写。

**学到的概念**
- **静默失败（silent failure）**：出错了却没有任何提示。这里“超字数被丢弃”就是静默失败：用户只看到“AI 建议修改 1 处”，不知道还有 2 处被扔掉了。生产系统里，这类情况至少要记日志。
- **假设驱动的调试**：先提出猜测，再设计一个能推翻它的检查，看证据说话。猜错不可怕，**不验证就下结论**才可怕。这次两个猜测都被推翻了，第三次才找到真相。
- **截获（interception）**：不改动被测代码，从外面拦截它的网络请求来观察内部行为。这里是把 `fetch` 包了一层，记录模型的原始回复。

## 答疑：为什么先测简历定制，而不是直接做 agent？

## 行动 11：搭出简历 agent 的最小原型

**日期**：2026-10-06

**做了什么**
在 `apps/api/src/agent/` 下新建了 4 个文件，加上 1 个测试文件，做出一个能在命令行里对话的简历 agent。

| 文件 | 作用 | 对应讲解文档第 3 节的零件 |
|---|---|---|
| `loop.ts` | agent 循环：调模型 → 有工具调用就执行 → 结果交回模型 → 直到模型用文字回复 | ④ 循环 |
| `model.ts` | 调用 DeepSeek（兼容 OpenAI 格式的接口），把工具清单一起发过去 | ① 模型 |
| `resume-coach.ts` | 3 个工具 + 系统提示词 | ② 提示词、③ 工具、⑥ 护栏 |
| `cli.ts` | 命令行入口：实时显示每一步，结束后保存完整轨迹 | ⑦ 可观测性 |
| `tests/agent-loop.test.mjs` | 用“假模型”测试循环本身 | — |

还做了一个结构调整：把编造检测器从 `evals/graders/` 移到 `src/agent/fabrication.ts`。它现在既是评分器，也是 agent 的线上护栏；产品代码不应该依赖评测代码，所以让评测代码反过来引用它。

**为什么这样设计**

1. **循环只有约 60 行**（`loop.ts`）。核心就是讲解文档里那段伪代码：
   ```text
   最多 8 步：
     调模型
     如果模型直接用文字回复 → 本轮结束（可能是最终答案，也可能是一个问题）
     否则逐个执行它要调用的工具，把结果放回对话，继续
   ```
   **追问不需要专门的工具**：模型用文字回复一个问题，本轮就结束了，等用户回答后进入下一轮。

2. **工具报错不让程序崩溃**：工具抛出的错误、调用不存在的工具，都会作为结果交回给模型，让它自己纠正。

3. **3 个工具**：

| 工具 | 作用 |
|---|---|
| `get_resume` | 读取简历，按条目返回，每条有 id |
| `get_job` | 读取目标岗位的职责和要求 |
| `propose_rewrite` | 提交一条改写稿。**工具内部用编造检测器检查**：数字、技术名、职责强度在简历原文和用户本次对话里说过的话中都要找得到出处，找不到就退回，并告诉模型是哪里没有出处 |

   **用户的回答自动算作证据**：用户说“一共写了 40 多篇”，改写里出现 40 就能通过。这就是“新增事实可追溯”的实现。

4. **护栏在代码里，不只在提示词里**：提示词要求“不能编造”（请求），`propose_rewrite` 用代码检查（保证）。模型就算不听话，编造的内容也进不了最终结果。

5. **系统提示词把“写法问题”和“素材问题”分开**：经历有、只是没写清楚的，直接改；缺规模、数字、结果的，先问用户，一次最多问 3 个具体问题，问完就停下等回答。

**学到的概念**
- **Function calling 的数据格式**：发给模型的是工具的名字、说明和参数格式（JSON Schema）；模型返回 `tool_calls`，里面有工具名和参数；程序执行后，用 `role: "tool"` 的消息把结果交回去，并用 `tool_call_id` 对应到是哪一次调用。
- **假模型（mock）测试**：循环的逻辑（执行工具、处理报错、步数上限）不需要真的调用模型就能测。写一个按剧本回复的假模型，测试又快又稳定。
- **并行工具调用**：模型可以在一次回复里同时调用多个工具（比如同时读简历和岗位），所以“2 步”就能完成 4 次工具调用。

**结果**
新增 4 个单元测试，全部通过（API 测试总数 78 个，全部通过；类型检查无报错）。

最后的参数可以换成考卷里任意一道题的 id，比如 `accounting-to-operations`、`game-ops-to-pm`。你来扮演候选人，试着：正常回答、说“记不清了”、要求它编数据，看它怎么反应。
