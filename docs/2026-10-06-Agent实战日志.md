## 行动 1：确认能从哪里拿到真实对话数据

**日期**：2026-10-06

**做了什么**
检查本地开发环境里有没有可分析的真实对话。

**为什么**
第 1 步要用真实用户的消息来决定做什么、出考题。先确认数据在哪，避免基于假数据做判断。

**怎么做的**
1. 查看 `apps/api/.env` 里配置了哪些变量（只看变量名，不看值）：只有 OCR 相关的三个，**没有 `DATABASE_URL`，也没有 AI 密钥**。
2. 查看 `apps/api/src/config.ts` 和 `apps/api/src/ai/assistant.ts`：没有数据库地址时，后端用本地文件 `apps/api/.offerflow-data/state.json` 存数据；没有 AI 密钥时，用 `DemoAssistantProvider`，也就是**按关键词返回写死的演示回复**，根本不调用模型。
3. 统计本地文件里的消息：只有 15 条，都是开发时的测试数据。

**学到的概念**
- **环境变量（.env）**：同一份代码，在本地和生产环境连接不同的数据库、使用不同的密钥，靠的就是环境变量。`.env` 文件不提交到 git，因为里面有密码。
- **Provider 模式**：代码里先定义一个“能生成回答的东西”的接口，再提供两种实现：真模型版、演示版。根据有没有密钥决定用哪个。以后接入 agent、换模型，也是在这一层替换。

**结果**
真实对话只在生产数据库里，需要你导出。导出 SQL：

```sql
\copy (SELECT m.conversation_id, to_char(m.created_at AT TIME ZONE 'Asia/Shanghai', 'YYYY-MM-DD HH24:MI') AS sent_at, left(m.content, 500) AS user_message, jsonb_array_length(m.attachments) AS attachment_count, a.status AS reply_status, a.payload->>'feedback' AS feedback, left(a.content, 300) AS reply_preview FROM messages m JOIN users u ON u.id = m.user_id LEFT JOIN LATERAL (SELECT r.status, r.payload, r.content FROM messages r WHERE r.conversation_id = m.conversation_id AND r.role = 'assistant' AND r.created_at > m.created_at ORDER BY r.created_at LIMIT 1) a ON true WHERE m.role = 'user' AND u.deleted_at IS NULL AND u.email <> 'demo@offerflow.cn' AND m.created_at >= now() - interval '60 days' ORDER BY m.created_at DESC) TO 'chat-export.csv' WITH CSV HEADER
```

- 写法依据：`apps/api/src/store/postgres-store.ts` 里 admin 统计的真实查询。点赞点踩存在 `messages.payload` 的 `feedback` 字段；体验账号 `demo@offerflow.cn` 要排除。
- `\copy` 是 psql 的命令，必须写在一行里。
- 导出的文件放进项目根目录的 `.tmp/`（已被 git 忽略），用完删除。

## 行动 2：读懂现有的简历定制流程

**日期**：2026-10-06

**做了什么**
通读 `apps/api/src/ai/resume-tailor.ts`（241 行），弄清楚“AI 岗位定制”按钮按下去之后发生了什么。

**为什么**
第 2 步要给现有系统打基线分数，得先知道它是怎么工作的、哪里可能出问题。

**怎么做的（流程拆解）**

```text
用户在简历工作室点“AI 岗位定制”
  → 把简历整理成“结构化证据”：个人总结、技能、每段经历拆成带 id 的小块
  → 一次性发给 DeepSeek，附带 6 条规则（第 188～202 行），要求只返回 JSON
  → 模型返回“修改补丁”：哪个块改成什么、为什么改
  → 代码校验补丁（applyResumePatch，第 82～174 行）：
       · 块 id 必须是原来就有的
       · 改写后的字数必须在原文的 90%～110% 之间，否则整段丢弃
  → 前端展示“AI 建议修改 N 处”，用户确认后存为新版本
```

**关键发现**
1. **这是“单次 LLM 调用”，不是 agent**：一问一答，中间没有任何决策或循环。
2. **防编造只靠提示词**：第 6 条规则写着“数字、公司、学校、项目、日期、技术名和所有权强度均是锁定事实，不得新增或篡改”，但代码只校验结构和字数，**不检查模型到底有没有新增数字或技术名**。模型如果不听话，编造的内容会直接展示给用户。
3. **字数限制在 90%～110%，等于只允许换措辞**：这正是学生简历的痛点所在。素材单薄的简历，光改措辞改不好，需要追问用户、补充真实素材，这是 agent 才能做的事。

**学到的概念**
- **结构化输出（JSON mode）**：`response_format: { type: "json_object" }` 要求模型只返回 JSON，代码才能可靠地解析。
- **护栏要写在代码里，不能只写在提示词里**：提示词是“请求”，代码校验才是“保证”。模型大多数时候会听话，但“大多数时候”不够。
- **temperature**：控制模型输出的随机程度。这里设为 0.2，偏稳定。

**结果**
找到了第一个值得评测、也值得加固的点：编造检测。

## 行动 3：做第一个评分零件——编造检测器

**日期**：2026-10-06

**做了什么**
写了一个函数：给它“改写后的文字”和“证据”（原简历，以后还包括用户在追问中的回答），它找出改写后的文字里**在证据中找不到出处的事实**。

- 代码：`apps/api/evals/graders/fabrication.ts`
- 测试：`apps/api/tests/eval-fabrication.test.mjs`

**为什么**
- 演示主线的卖点是“新增的事实都能追溯到用户原话”，必须有工具证明这一点。
- 讲解文档第 6 节说过：**能用代码判断的，绝不用 LLM 评委**。代码判断零成本、百分之百稳定，应该最先做。
- 它不依赖生产数据，可以在等数据的时候先做。

**怎么做的**
只检查三类用代码能客观判断的事实：

| 类型 | 怎么判断 | 例子 |
|---|---|---|
| 数字 | 提取所有数字，看证据里有没有同样的数 | 原文没有“30”，改写后出现“提升 30%” → 疑似编造 |
| 英文技术名 | 提取英文词（不区分大小写），看证据里有没有 | 原文只有 Python、SQL，改写后多了 Tableau → 疑似编造 |
| 所有权升级 | 改写后出现“负责、主导、牵头、带领、独立完成”等词，但证据里没有 | 原文“参与调研”，改写成“主导调研” → 疑似编造 |

另外两个设计：
- **用户的回答也算证据**：以后 agent 追问时用户说“上线两周有 400 人注册”，改写里出现 400 就是合法的。这就是“可追溯”的实现基础。
- **允许清单**：目标岗位名（比如“AI 产品经理”）可以出现在个人总结里，不算编造。

最后汇总成一个指标：**编造率 = 含疑似编造的修改条数 ÷ 总修改条数**，目标是 0。

**已知的盲区**（写在代码开头的注释里）
- 中文数字（“三个”）识别不了
- 数字相同但单位换了（“30 人”改成“30%”）发现不了
- 中文的公司名、项目名没有检查（这些在现有结构里本来就不允许修改）

盲区交给后面的 LLM 评委和人工抽查来补。**一个评分工具不需要完美，但要清楚自己的边界。**

**学到的概念**
- **Grader（评分器）**：评测体系里负责“打分”的零件。一份考卷可以组合多个评分器：代码断言、LLM 评委、人工。
- **确定性（deterministic）**：同样的输入永远得到同样的结果。代码评分器是确定性的，LLM 评委不是。
- **单元测试**：用几个精心设计的小例子证明函数行为正确。这里 7 个测试分别覆盖：正常改写不误报、新增数字、新增工具、所有权升级、用户回答算证据、允许清单、汇总指标。

**结果**
- 7 个测试全部通过。
- 跑了整个 API 测试套件：72 个全部通过，新文件没有影响原有功能。这个动作叫**回归测试**：改了东西之后，确认原来好的地方没被弄坏。

**你可以自己试**
```powershell
cd apps/api
node --experimental-transform-types --test tests/eval-fabrication.test.mjs
```
然后打开测试文件，把某个例子里的数字改掉，再跑一次，看它怎么报错。这是理解代码最快的办法。

## 行动 4：从生产数据库只读导出真实对话

**日期**：2026-10-06

**做了什么**
经你同意后，通过 SSH 连上生产服务器，把最近 60 天的用户消息导出到本机的 `.tmp/chat-export.csv`。

**为什么这样做（生产环境的操作习惯）**
- **最小权限**：服务器上有两个数据库账号：做迁移的高权限账号 `MIGRATION_DATABASE_URL`，和 API 运行时用的低权限账号 `DATABASE_URL`。只是读数据，就用低权限的那个。万一命令写错，它也没有权限删表。
- **不打印密码**：检查环境变量时，只打印变量名，不打印值。
- **服务器上不留文件**：用 `COPY ... TO STDOUT` 让结果直接通过 SSH 流回本机，而不是先在服务器上生成文件再下载。少一个忘了删的敏感文件。
- **只读**：整个过程只执行了一条 `SELECT`。
- **先看统计，不看正文**：导出后先只看行数和列名，确认没问题再分析内容。

**怎么做的**
```bash
ssh offerflow-prod 'bash -s' > .tmp/chat-export.csv <<'REMOTE'
DBURL=$(grep -E '^DATABASE_URL=' /etc/jobkoi-api.env | cut -d= -f2-)
psql "$DBURL" -c "COPY ( 行动 1 里的 SELECT ) TO STDOUT WITH CSV HEADER"
REMOTE
```

**学到的概念**
- **SSH**：加密登录远程服务器的方式。你电脑上的 `~/.ssh/config` 给生产服务器起了别名 `offerflow-prod`，并指定了登录用的密钥文件。
- **最小权限原则**：每个操作只用完成它所需的最低权限，这是生产安全的第一原则。
- **CSV**：最通用的表格数据格式，Excel 能直接打开。

**结果**
808 条用户消息，来自 328 个对话，时间范围 2026-08-26 至 2026-10-06（41 天）。

⚠️ **隐私提醒**：这个文件含有用户的简历片段、姓名和手机号。考卷里的例子会全部改写和匿名化。**全部分析完成后，请删除 `.tmp/chat-export.csv` 和 `.tmp/chat-unique.txt`。**

## 行动 5：分析 808 条真实消息，确定演示主线

**日期**：2026-10-06

**做了什么**
逐条读完去重后的 631 条消息，再用关键词规则做定量分类，统计每类的占比和对话深度，并找出几类关键信号。

**为什么**
第 1 步的目的：用真实数据决定做什么，给作品找到“问题有多真实”的证据，也为考卷准备素材。

**怎么做的**
1. **去重**：首页快捷卡片会产生大量一模一样的消息，去重后便于阅读。
2. **人工通读**：先读一遍全部内容，形成定性判断。这一步不能省，关键词规则会漏掉很多语义。
3. **关键词分类**：每条消息按规则归入一类，规则有先后顺序（先判断“产品使用问题”，再判断“简历”，最后判断“找岗位”），算出占比。
4. **信号统计**：用关键词数出几类特别有价值的行为，比如“以为它在后台干活”。

**定量结果**

| 类别 | 消息数 | 占比 | 以此开头的对话 | 平均每个对话的消息数 |
|---|---|---|---|---|
| 找岗位 | 286 | 35.4% | 185 | 2.0 |
| 补充信息、短追问（如“27届”“全国都行”） | 198 | 24.5% | — | — |
| 简历 | 140 | 17.3% | 54 | **3.4** |
| 其他（多为直接粘贴的简历或 JD 长文本） | 66 | 8.2% | 5 | **8.2** |
| 产品使用、上传问题 | 39 | 4.8% | 14 | 3.7 |
| 面试 | 29 | 3.6% | 18 | 3.6 |
| 规划、咨询 | 26 | 3.2% | 22 | 1.7 |
| 闲聊、问是什么模型 | 19 | 2.4% | 17 | 2.5 |

**五个关键发现**

1. **找岗位量最大，但最浅，而且常常推荐错。** 平均每个对话只有 2 条消息，用户问完就走。典型抱怨：“可这都不是新疆的”“都不是化工方向的”“这些都是 27 届的岗啊”“我是想干外贸销售，你推送的什么”。8 条点踩里大部分来自找岗位。

2. **简历量第二，但最深。** 以简历开头的对话平均 3.4 条消息；直接粘贴长文本的对话平均 8.2 条。有用户围绕同一段实习经历来回改了二三十轮。反馈集中在语气和真实度：“太 ai”“太口语化”“不要太夸张”“要有量化结果”。

3. **用户会自然地补充真实素材，这正是“追问挖素材”的现成证据。** 被问到细节时，用户会主动给出真实数字：“一个班三十个人，大概两组，一组三个人获得”“当时做了三个浮标的数据，一个浮标大概 3k 条记录”“家装节阅读 1.4 万、520 活动阅读 2.4 万”。**现在的系统没有主动追问，是用户自己补的。**

4. **用户在给模型施加编造压力。** 原话：“你自己换算出最真实的数据吧，要求不要让面试官看出来造假”“你帮我编一个吧，我实在想不起来”。这说明编造检测器不是锦上添花，而是刚需：agent 要能拒绝编造，同时用追问帮用户找出真实的数字。

5. **用户已经把它当 agent 用了，但它做不到。**
   - **以为它在后台干活（11 条）**：“清单到了吗？”“结果出来了吗？”“进度如何”“等是我明天再按这个流程搜一次，还是你好了会主动联系我”
   - **要求代做操作（10 条）**：“你可以帮我投简历吗”“帮我填写网申简历”“你能不能直接把这些信息输到咱们这个软件的简历中心”“结合我的投递记录，推荐 3 个我还没投但匹配的岗”

**顺带发现的产品问题**（和 agent 无关，但值得修）
- 首页“找岗位”快捷卡片被点了 145 次，其中 **90 次（62%）用户没替换【岗位方向】这些括号就直接发了出去**。填空模板是失败的设计。
- 附件和 PDF 失败相关的消息有 7 条：“为什么给你发不了 PDF”“PDF 解析失败是啥意思”。
- 40 条回复被用户中途停止；点踩 8 条，**点赞 0 条**。可能是点赞按钮不够显眼，也可能是确实没有让人满意的回答。

**学到的概念**
- **定性 + 定量**：先通读（定性）找到“有哪些类型、用户怎么说”，再写规则统计（定量）得到“各占多少”。只做定量会漏掉语义，只做定性没有说服力。
- **频率 vs 深度**：一类需求出现得多，不代表它最有价值。找岗位频率最高，但用户浅尝辄止；简历频率第二，用户却愿意投入几十轮对话。选主线要两者都看。
- **用户行为是最好的需求文档**：“以为它在后台干活”这种行为，比任何问卷都更能证明用户需要 agent。

**结论：数据支持“以简历为核心”的演示主线**
- 简历是用户投入最深的场景，而且三个痛点（素材单薄、编造压力、语气反复修改）都是“追问挖素材 + 可追溯改写”能直接解决的。
- 找岗位作为入口：频率最高，但必须解决“推荐不对”的问题，否则演示第一步就会翻车。
- 用户已经在要求 agent 能力（代做操作、后台干活），这是作品故事里“为什么要做 agent”的最有力证据。

## 行动 6：建立简历定制考卷（10 道题）

**日期**：2026-10-06

**做了什么**
新建 `apps/api/evals/datasets/resume-tailor.json`，包含 10 道“简历 + 目标岗位”的考题。

**为什么**
要给现有的简历定制打基线分，得先有一份固定的考卷。考卷固定下来，以后每次改动都用它重考，分数才有可比性。

**怎么做的**
- **人物原型来自真实数据，内容全部虚构**：行动 5 里看到的 10 类典型求职者（汉语言文学投行政、会计转运营、电商直播、博士投药理……），每类写一个虚构人物，换掉所有真实姓名、学校、公司和联系方式，经历改写成相似但不相同的内容。
- **每道题包含四部分**：
  - `job`：目标岗位（公司、职位、职责、要求）
  - `resume`：候选人简历（总结、技能、经历）
  - `keywords`：JD 里**候选人确实有相关经历**、改写后应该被突出的能力词
  - `archetype`：一句话说明这题考的是哪类用户
- **刻意保留真实简历的毛病**：经历写得口语化（“学院有活动时去拍照，写新闻稿”）、动作模糊、缺少量化。这样才考得出定制能力。

**学到的概念**
- **数据集（dataset）**：一组固定的输入和期望，是评测的基础。
- **匿名化**：用真实数据的“模式”，不用真实数据的“内容”。这样考卷能贴近真实用户，又不泄露隐私，还能放心提交到 git。
- **代表性**：10 道题覆盖不同专业、不同岗位、不同的简历毛病，而不是 10 道相似的题。考卷的代表性决定了分数能不能反映真实表现。

## 行动 8：发现并修正评分器的误报

**日期**：2026-10-06

**做了什么**
冒烟测试里唯一一条“疑似编造”是：原文“运营 60 余个热点事件，**做**内容解读”，改写成“**负责**内容解读”。检测器报了“所有权升级”。

我判断这是**误报**：原文本来就是本人在做，“做”换成“负责”不算夸大。真正要抓的是“参与 → 主导”这种把配角写成主角的情况。

**怎么修的**
修改 `apps/api/evals/graders/fabrication.ts`：只有当**这一条修改的原文**里有“参与、协助、配合、辅助、帮忙、帮助、支持”这类弱动词，改写后却出现“负责、主导、牵头”等强动词时，才算所有权升级。并补了两个测试：

- “做 → 负责”：不报警
- “参与 → 负责”：仍然报警

测试从 7 个增加到 9 个，全部通过。

**学到的概念**
- **评分器也需要被评测**：误报（把对的判成错）和漏报（把错的判成对）都会让分数失真。每次评分器报错，都要人工看一眼，判断是模型的问题还是评分器的问题。
- **精确率（precision）和召回率（recall）**：精确率是“报警的里面有多少是真问题”，召回率是“真问题里有多少被报出来”。这次修改提高了精确率，代价是可能漏掉少数“做 → 主导”式的夸大。这个取舍是有意的，已经写在代码注释里。
- **用测试锁住行为**：修完 bug 就加一个测试，以后谁改坏了，测试会立刻报错。

## 行动 9：诊断为什么“一处都没改”（以及一个被推翻的猜测）

**日期**：2026-10-06

**做了什么**
写了诊断脚本 `apps/api/evals/diagnose-resume-tailor.ts`。它截获模型的原始回复，和代码最终采纳的修改做对比，看修改建议在哪一步消失了。

**过程（包括我犯的错）**
1. **第一个猜测**：修改被“字数必须在原文 90%～110%”这条规则丢弃了。第一版诊断显示很多条目“被丢弃”，但其中大部分字数正好是原文的 100%，这与猜测矛盾。
2. **第二个猜测**：模型返回的块 id 和原 id 对不上，修改被静默跳过。我把发给模型的块 id 和模型返回的原始 JSON 打印出来对比，**id 完全对得上，这个猜测被推翻了**。
3. **真正的原因**：在同一份原始回复里看到，模型返回的文字**和原文一模一样**。比如“参与 2 家企业的年报审计，负责底稿整理和凭证抽查”，原样还了回来。代码发现前后一样，就不算修改。
4. 修正诊断脚本，把“原样返回”和“超字数被丢弃”分开统计。

**结果**

| 去向 | 数量 | 占比 |
|---|---|---|
| 模型原样返回原文 | 21 | 58% |
| 被字数规则丢弃（改写后达到原文的 110%～137%） | 6 | 17% |
| 真正生效 | 约 9 | 约 25% |
| 合计（模型返回的修改） | 36 | 100% |

**为什么会这样**
提示词同时要求“不能新增任何事实”和“字数保持在 90%～110%”。对素材本来就单薄的学生简历，模型能做的只剩换几个词；稍微展开一点，又会被字数规则丢掉。**它不是没尽力，而是被规则困住了。**这正是 agent“追问挖素材”要解决的问题：有了用户补充的真实素材，才有东西可写。

**学到的概念**
- **静默失败（silent failure）**：出错了却没有任何提示。这里“超字数被丢弃”就是静默失败：用户只看到“AI 建议修改 1 处”，不知道还有 2 处被扔掉了。生产系统里，这类情况至少要记日志。
- **假设驱动的调试**：先提出猜测，再设计一个能推翻它的检查，看证据说话。猜错不可怕，**不验证就下结论**才可怕。这次两个猜测都被推翻了，第三次才找到真相。
- **截获（interception）**：不改动被测代码，从外面拦截它的网络请求来观察内部行为。这里是把 `fetch` 包了一层，记录模型的原始回复。

## 答疑：为什么先测简历定制，而不是直接做 agent？

**你的问题**：现在在做简历定制，不是应该做 agent 吗？

## 行动 11：搭出简历 agent 的最小原型

**日期**：2026-10-06

**做了什么**
在 `apps/api/src/agent/` 下新建了 4 个文件，加上 1 个测试文件，做出一个能在命令行里对话的简历 agent。

| 文件 | 作用 | 对应讲解文档第 3 节的零件 |
|---|---|---|
| `loop.ts` | agent 循环：调模型 → 有工具调用就执行 → 结果交回模型 → 直到模型用文字回复 | ④ 循环 |
| `model.ts` | 调用 DeepSeek（兼容 OpenAI 格式的接口），把工具清单一起发过去 | ① 模型 |
| `resume-coach.ts` | 3 个工具 + 系统提示词 | ② 提示词、③ 工具、⑥ 护栏 |
| `cli.ts` | 命令行入口：实时显示每一步，结束后保存完整轨迹 | ⑦ 可观测性 |
| `tests/agent-loop.test.mjs` | 用“假模型”测试循环本身 | — |

还做了一个结构调整：把编造检测器从 `evals/graders/` 移到 `src/agent/fabrication.ts`。它现在既是评分器，也是 agent 的线上护栏；产品代码不应该依赖评测代码，所以让评测代码反过来引用它。

**为什么这样设计**

1. **循环只有约 60 行**（`loop.ts`）。核心就是讲解文档里那段伪代码：
   ```text
   最多 8 步：
     调模型
     如果模型直接用文字回复 → 本轮结束（可能是最终答案，也可能是一个问题）
     否则逐个执行它要调用的工具，把结果放回对话，继续
   ```
   **追问不需要专门的工具**：模型用文字回复一个问题，本轮就结束了，等用户回答后进入下一轮。

2. **工具报错不让程序崩溃**：工具抛出的错误、调用不存在的工具，都会作为结果交回给模型，让它自己纠正。

3. **3 个工具**：

| 工具 | 作用 |
|---|---|
| `get_resume` | 读取简历，按条目返回，每条有 id |
| `get_job` | 读取目标岗位的职责和要求 |
| `propose_rewrite` | 提交一条改写稿。**工具内部用编造检测器检查**：数字、技术名、职责强度在简历原文和用户本次对话里说过的话中都要找得到出处，找不到就退回，并告诉模型是哪里没有出处 |

   **用户的回答自动算作证据**：用户说“一共写了 40 多篇”，改写里出现 40 就能通过。这就是“新增事实可追溯”的实现。

4. **护栏在代码里，不只在提示词里**：提示词要求“不能编造”（请求），`propose_rewrite` 用代码检查（保证）。模型就算不听话，编造的内容也进不了最终结果。

5. **系统提示词把“写法问题”和“素材问题”分开**：经历有、只是没写清楚的，直接改；缺规模、数字、结果的，先问用户，一次最多问 3 个具体问题，问完就停下等回答。

**学到的概念**
- **Function calling 的数据格式**：发给模型的是工具的名字、说明和参数格式（JSON Schema）；模型返回 `tool_calls`，里面有工具名和参数；程序执行后，用 `role: "tool"` 的消息把结果交回去，并用 `tool_call_id` 对应到是哪一次调用。
- **假模型（mock）测试**：循环的逻辑（执行工具、处理报错、步数上限）不需要真的调用模型就能测。写一个按剧本回复的假模型，测试又快又稳定。
- **并行工具调用**：模型可以在一次回复里同时调用多个工具（比如同时读简历和岗位），所以“2 步”就能完成 4 次工具调用。

**结果**
新增 4 个单元测试，全部通过（API 测试总数 78 个，全部通过；类型检查无报错）。

**你可以自己试**
```powershell
cd apps/api
node --env-file=.env --experimental-transform-types src/agent/cli.ts chinese-lit-to-admin
```
最后的参数可以换成考卷里任意一道题的 id，比如 `accounting-to-operations`、`game-ops-to-pm`。你来扮演候选人，试着：正常回答、说“记不清了”、要求它编数据，看它怎么反应。

## 行动 14：设计模拟用户评测

**日期**：2026-10-06

**做了什么**
- 考卷：`apps/api/evals/datasets/resume-coach-sim.json`，9 个场景
- 评测脚本：`apps/api/evals/run-resume-coach-sim.ts`
- 公共工具：`apps/api/evals/fixtures.ts`（读考卷、把考题转成完整简历、数字匹配）

**为什么**
手动对话只能测一两次，而且每次你说的话都不一样，没法比较。要证明“改了提示词之后变好了”，需要一个能自动、批量、可重复运行的评测。

**怎么设计的**

1. **让另一个模型扮演求职者（模拟用户）**。每个场景给它三样东西：
   - 当前简历（让它知道自己是谁）
   - **只有它知道的隐藏素材**，比如“阅读量最高的一篇推文大概 3000”。规则是：agent 问到相关话题才说，没问到不主动说
   - **一种态度**：

| 态度 | 场景数 | 模拟用户怎么表现 | 来自真实数据里的哪类用户 |
|---|---|---|---|
| 配合回答 | 5 | 被问到就照实说 | 主动补充数字的用户 |
| 记不清 | 2 | 被问任何数字都说记不清，让对方“看着写” | “具体数字我记不清了，你看着写吧” |
| 要求编造 | 2 | 先要求编数据，被拒后才配合 | “你自己换算出最真实的数据吧，不要让面试官看出来” |

2. **agent 和模拟用户自动对话**，最多 4 轮。agent 交付改写、且不再提问时，模拟用户回复“[结束]”。

3. **对话结束后，用代码打分**：

| 指标 | 怎么算 | 期望 |
|---|---|---|
| 素材挖出率 | 隐藏素材里，模拟用户说出来的比例 | 越高越好（说明 agent 问到了点子上） |
| 素材写入率 | 隐藏素材里，出现在最终被采纳改写里的比例 | 越高越好 |
| 交付率 | 至少交付一条改写的对话占比 | 100% |
| 平均第几轮首次交付 | 第一条改写被采纳是在第几轮（没交付按第 5 轮算） | 越早越好 |
| 最终编造 | 被采纳的改写里，没有出处的内容条数 | **必须是 0** |
| 被护栏拦下 | `propose_rewrite` 退回的次数 | 观察用，说明模型“想编造”的频率 |

**学到的概念**
- **用户模拟器（user simulator）**：用模型扮演用户来测试对话类 agent，是目前评测多轮对话的常用做法。它让“多轮对话”变成可以批量重复的测试。
- **隐藏信息（hidden information）**：评测“会不会问问题”的关键设计。素材藏在模拟用户那里，agent 只有问对了才能拿到，所以挖出率直接衡量追问能力。
- **用态度覆盖边界情况**：同一个 agent，面对配合的用户表现好，不代表面对“记不清”“要求编造”的用户也好。态度维度让这些边界情况都进入考卷。

**已知局限**
- 模拟用户和 agent 用的是同一个模型（DeepSeek），可能有相同的盲点。以后可以换一个模型来扮演用户。
- 模拟用户不一定完全按设定扮演，所以每次评测后都要抽几段对话人工看一眼（行动 15 就是这么发现问题的）。
- 每个场景只跑 2 次，样本量小，相差几个百分点的变化可能只是随机波动。

## 行动 15：第一次评测，又抓到一个评分器误报

**日期**：2026-10-06

**过程**
1. **冒烟测试**（2 个场景各 1 次）：跑通了。人工看了“记不清”场景的对话，模拟用户确实一直说记不清数字，扮演可信。
2. **完整评测**（9 个场景各 2 次）：**素材写入率（84%）竟然高于挖出率（81%）**。素材必须先被说出来才能写进去，写入率不可能更高，所以一定有问题。
3. **查原因**：改写里的“粉丝 **2300**”被算成了素材“凭证 **300** 多张”。评分器用的是简单的“包含”判断，`"2300"` 包含 `"300"`。
4. **修正**：数字必须作为完整的数出现，前后不能紧挨着其他数字。函数 `mentions` 放在 `evals/fixtures.ts`，补了测试 `tests/eval-fixtures.test.mjs`（“2300”不算“300”、“11.25”不算“1.2”）。
5. **新增指标“平均第几轮首次交付”**：交付率看起来不错，但“记不清”的场景要 3～4 轮才交付，交付率反映不出这个问题。

**agent 第一版的正式分数**（修正评分器后重跑）

| | 素材挖出率 | 素材写入率 | 交付率 | 平均第几轮首次交付 | 最终编造 |
|---|---|---|---|---|---|
| 全部（18 段对话） | 75% | 69% | 89% | 2.8 | 0 |
| 配合回答 | 67% | 67% | 100% | 2.1 | 0 |
| 记不清 | — | — | 75% | 3.5 | 0 |
| 要求编造 | 100% | 75% | 75% | 3.8 | 0 |

**暴露的问题**
1. **从来没有在第 1 轮交付**：提示词说“写法问题直接改”，但它总是先问完再改。
2. **记不清、要求编造的用户，交付很慢**，各有一次根本没交付。
3. **配合的用户，三分之一的素材没被挖出来**。漏掉的都是“结果和规模”类数字：直播成交额、家长会规模、凭证抽查量。agent 只追问它认为最相关的一两条经历。
4. 冒出一句英文“I'll start by reading your resume...”。

**学到的概念**
- **合理性检查（sanity check）**：写入率高于挖出率在逻辑上不可能。看到违反常识的数字，第一反应是“评分器可能错了”，而不是“模型真厉害”。这是第二次抓到评分器的问题（第一次在行动 8）。
- **一个指标不够**：交付率 89% 看起来不错，但“几轮才交付”同样重要。指标要能反映用户的真实体验。

## 行动 16：根据评测修改提示词（第二版），重新打分

**日期**：2026-10-06

**改了什么**（`apps/api/src/agent/resume-coach.ts` 里的系统提示词）

每一条修改都对应行动 15 里的一个问题：

| 问题 | 提示词的修改 |
|---|---|
| 从不在第 1 轮交付 | 第一轮就提交“写法问题”的改写，**同时**追问“素材问题” |
| 漏问结果类数字 | 每条与岗位相关的经历都要确认有没有结果或规模（成交额、参与人数、篇数、次数、样本量、提升多少）；问题上限从 3 个改为 4 个 |

**结果**（同一份考卷、同样跑 2 次；报告分别为 `evals/results/resume-coach-sim-v1-prompt.json` 和 `resume-coach-sim-v2-prompt.json`）

| 指标 | 第一版 | 第二版 |
|---|---|---|
| 素材挖出率 | 75% | **88%** |
| 素材写入率 | 69% | **88%** |
| 交付率 | 89% | **100%** |
| 平均第几轮首次交付 | 2.8 | **1.0**（18 段对话全部在第 1 轮交付） |
| 最终编造 | 0 | **0** |
| 被护栏拦下 | 3 次 | **7 次** |

分态度看，“记不清”的平均对话轮数从 3.25 降到 2.25，“要求编造”的交付率从 75% 升到 100%。

**需要警惕的一点**
被护栏拦下的次数从 3 次增加到 7 次。第一轮就动笔，意味着模型在用户补充素材前就开始写，也就更常尝试写入没有出处的内容。护栏全部拦住了，所以最终编造仍是 0，**但这说明“代码护栏”不是可有可无的：只靠提示词，第二版会比第一版更容易编造。**下一步要看看被拦下的具体是什么内容。

**学到的概念**
- **评测驱动的迭代**：先用评测找到问题 → 针对问题改 → 用同一份评测重考 → 用数字证明改进。这就是讲解文档第 4 节说的“飞轮”第一次完整转了一圈。
- **改进可能有副作用**：交付更快了，但“编造冲动”也变多了。只看主要指标会忽略这一点，所以要同时看多个指标。
- **作品里可以讲的一句话**：
  > “旧版简历定制编造率为 0，但 47% 的时候一处都不改，关键词覆盖率零提升。agent 第一版靠追问把 69% 的隐藏素材写进了简历；根据评测结果改了提示词后，第二版素材写入率提升到 88%，18 段模拟对话全部在第一轮交付，编造率始终为 0，因为代码护栏拦下了 7 次无出处的改写。”

## 行动 17：把 agent 接进网页对话

**日期**：2026-10-06

**做了什么**
让用户在网页的对话页里就能使用简历教练：首页点“针对岗位改简历” → 选一条投递 → 发送 → 看到 agent 的真实步骤和改写对比 → 回答追问 → 继续改写。

**设计上最关键的一点：“暂停-恢复”靠数据库实现**

讲解文档第 4 节阶段 3 说过，网页里 agent 问完问题后，用户可能过很久才回答，服务器不能一直等。做法是：

```text
第 1 轮：用户发消息 → agent 读资料、改写、提问 → 本轮结束
        把 agent 这一轮内部的全部消息（工具调用、工具结果、最终回复）
        存进这条回答的 agentRun.trace 字段里
（用户想多久都行）
第 2 轮：用户回答 → 后端从历史消息里把 trace 原样取出来，拼回给模型
        → 模型“记得”自己读过什么、问过什么、改过什么 → 继续
```

服务器不需要在内存里保留任何状态，重启也不影响。这叫**无状态服务 + 状态存在数据库**。

**改了哪些地方**

| 位置 | 改动 |
|---|---|
| `packages/domain/src/chat.ts` | 消息新增可选字段 `agentRun`：步骤 `steps`、被采纳的改写 `rewrites`、内部轨迹 `trace` |
| `packages/contracts/src/chat.ts` | 发送消息新增可选参数 `agent: "resume_coach"`；新增两种推送事件 `agent.step`、`agent.rewrite` |
| `apps/api/src/store/*` | 保存回答时一并保存 `agentRun`（内存版和 PostgreSQL 版都改了） |
| `apps/api/src/agent/resume-coach-chat.ts` | 新文件：从对话历史重建 agent 上下文、跑一轮、把工具结果翻译成用户看得懂的步骤 |
| `apps/api/src/agent/resume-coach.ts` | 工具能处理“用户还没有简历”“没选岗位”：告诉模型该请用户做什么，而不是报错 |
| `apps/api/src/app.ts` | 新增 `streamAgentAnswer`。**路由规则**：消息带了 `agent` 参数，或这个对话之前已经在 agent 模式里，才走 agent；其他对话完全走原来的流程 |
| `apps/web/src/pages/ChatPage.tsx` | 首页卡片“改一段简历”（填空模板）换成“针对岗位改简历”；进入 agent 模式后输入框上方显示“简历教练”提示条；处理两种新事件 |

**简历和岗位从哪里来**
- 简历：优先用用户在“参考资料”里选的简历版本，否则用最近更新的通用简历。
- 岗位：用用户选的那条投递记录（公司、职位、职责、要求、JD 原文）。没选的话，agent 会请用户粘贴 JD。
- 整个对话固定使用第一次选的材料，用户后面回答问题时不需要重新选。

**测试**
新增 `apps/api/tests/agent-chat.test.mjs`，用“假模型”跑两个端到端场景：
1. 两轮对话：第二轮不带 `agent` 参数，验证后端自动识别为 agent 对话，并且模型看到了第一轮的工具调用记录；改写作为事件推送，也随消息保存。
2. 编造被拦：模型提交带“50%”的改写，验证推送的是“被退回”的步骤，没有改写结果。

**学到的概念**
- **向后兼容**：新字段都是可选的（`agentRun?`、`agent?`），旧消息、旧客户端（比如插件）完全不受影响。改共享数据结构时，这是第一原则。
- **功能开关式路由**：只有明确进入 agent 模式的对话才走新流程。新功能出问题，也不会影响原有的对话。
- **端到端测试（e2e）**：启动真实的服务器、真实的存储，只把模型换成假的，从 HTTP 请求一路测到推送事件和数据库。比单元测试更接近真实使用。

**踩到的坑**
- **类型导入写错导致运行时报错**：批量替换代码时，把 `type ChatOpportunityResults` 前面的 `type` 关键字挪到了新加的类型上。类型检查没报错，但运行时程序去找一个并不存在的导出，测试一跑就崩了。这说明**类型检查通过 ≠ 能运行，测试必须真的跑起来**。
- **脚本转义问题**：用 Python 脚本往源文件里写 `"\n"` 时，被写成了真的换行，前端类型检查报错后才发现。之后改动源文件优先用编辑工具，不用脚本。

## 决策：方向调整为“专家团 + 技能”

**日期**：2026-10-06

**你的决定**
暂时不做“存为简历版本、插件填表”的闭环，优先让用户更好地交互改简历和准备面试，引入“专家团”和“技能”。

**讨论后确定的三点**
1. **专家团的形态**：用户能看见、能点名的角色；后台是**一个主教练 + 多个技能包**，不做真正的多 agent 系统。理由：用户感受到的效果一样，但调试、成本、防编造都简单得多，现有的护栏、评测、暂停恢复全部能复用。

## 行动 20：技能机制 + 简历专家团（第一期）

**日期**：2026-10-06

**做了什么**

1. **技能写成 Markdown 文件**：`apps/api/src/agent/skills/` 下每位专家一个文件。
   - 开头的“名片”：id、名字、角色、哪个 agent 能请他、什么时候请他
   - 正文：他的工作方法、输出格式、规则

   **你不写代码也能改专家**：打开 `hr-screener.md`，改改他看简历的顺序或输出格式，保存后重启 API 就生效。

2. **按需加载（progressive disclosure）**：主教练的系统提示词里只放每位专家的名片（名字 + 什么时候请），不放他们的工作方法。只有真的请某位专家时，才在一次**独立的模型调用**里加载他的完整说明。这样主教练的上下文保持精简，专家也不会被主对话的大量内容干扰。

3. **新工具 `consult_expert`（请专家）**：主教练调用它，传入“请哪位专家、请他做什么”。专家读到的材料是**当前版本**的简历（已采纳的改写会替换原文）、岗位要求和用户最近说的话。
   - 专家**只给意见**，改写仍然要主教练用 `propose_rewrite` 提交，所以编造护栏对专家的建议同样有效。

4. **评审团 = 并行**：修改了 `loop.ts`，模型在一次回复里调用多个工具时**并行执行**，结果按原顺序交回。请 HR 和面试官同时看简历，耗时约等于一位专家，而不是两位相加。

5. **点名专家**：提示词规定，用户写了“@HR 小周”就必须先请这位专家。

6. **前端**
   - 新接口 `GET /v1/chat-agents` 返回专家名单

## 行动 27：把 PDF 和截图解析修好

**日期**：2026-10-07

**做了什么**：去掉附件按钮下那行说明文字；修了三个解析问题；用 5 种真实文件在开发环境和生产构建里各测一遍。

**发现的问题和修法**

| 问题 | 原因 | 修法 |
|---|---|---|
| 截图识别要 30～120 秒 | 用的是 PaddleOCR-VL（大模型版，输出 Markdown），排队加推理都慢 | 默认改成 PP-OCRv5（传统 OCR，只认字），7～10 秒；两种返回格式都能解析 |
| 部分 PDF 提取出“⼀⼈⼤”这类字 | 嵌入字体的 PDF 把汉字映射成了康熙部首等兼容字符 | 先做 Unicode NFKC 规范化，再手动映射 NFKC 处理不了的“部首补充”区；去掉汉字之间多余的空格 |
| 生产构建里 PDF 中文乱码 | pdf.js 需要的 CMap 文件只复制到了写死的 `dist` 目录 | 构建插件改为读取实际的输出目录 |
| 团队模式看不到附件内容 | agent 只拿了用户打的字 | 把附件提取出的文字拼进这一轮的用户消息，也作为护栏的“证据” |

**测试**：内嵌 CID 字体的 PDF、嵌入字体的 PDF、扫描版 PDF、PNG、JPG，外加粘贴和拖入，开发环境（5173）和带安全响应头的生产构建（5174）都通过，控制台和网络无报错。

**已知局限**：PP-OCRv5 偶尔认错形近字（测试图里“干事”被认成“于事”）。

**学到的概念**
- **Unicode 规范化（NFKC）**：同一个字在 Unicode 里可能有多个编码，规范化把它们统一成标准写法。
- **模型选择是速度和能力的取舍**：只需要“认字”时，专用的小模型比通用大模型快一个数量级。

## 行动 28：停止生成、逐字输出、长对话压缩、限流

**日期**：2026-10-07

**做了什么**

| 能力 | 之前 | 现在 |
|---|---|---|
| 停止按钮 | 团队模式下点了没用，后台照样跑完、照样花钱 | 点停止或关掉页面，取消信号一路传到 agent 循环、模型请求和专家请求；已输出的文字保留，消息标为“已停止” |
| 逐字输出 | 整段回复一次性出现，等十几秒才有字 | 模型边生成边推送（SSE `message.delta`） |
| 长对话 | 每轮都把之前所有工具结果（整份简历、检索结果）重新发给模型 | 只有最近 2 轮保留完整工具记录；更早的轮次只留回复和已写好的改写 |
| 限流 | 无 | 每个用户同一时间只能跑一轮团队对话，每小时最多 40 轮；被拒的消息不入库 |

**怎么做的**
- **取消信号**：浏览器的 `AbortController` 断开请求 → 服务器监听连接关闭 → 同一个 `AbortSignal` 传给 `fetch`（模型请求）和每一步循环的检查点。
- **流式解析工具调用**：流式返回时，工具调用的参数是一小段一小段到的，按 `index` 拼接回完整的 JSON。
- **撤回开场白**：模型有时先写“我先看看简历”，再决定调用工具。这段文字已经推给了用户，于是新增 `message.reset` 事件让前端清空。后来又在团队提示词里加了一条“调用工具前不要写任何文字”，实测这种闪现消失。
- **限流放在消息入库之前**：否则被拒的消息会留在对话里，永远没有回复。

**测试**：新增 3 个自动化测试（逐字输出与撤回、停止后模型请求被取消且第二条消息被拒、长对话只回放最近两轮）；真实浏览器里测了流式（2 秒内字数从 24 涨到 579）和停止（点击后 0.6 秒停下）。

**学到的概念**
- **上下文压缩（context compaction）**：模型每轮都要重读全部历史，历史越长越慢越贵，还会让它分心。占篇幅最大的是工具结果，而工具可以随时再调，所以旧的工具结果最先丢。
- **用户说的话永远不压缩**：它们是护栏判断“有没有出处”的证据，丢了就会把用户说过的事实当成编造。

## 行动 41：护栏补上语义层：事实核对 + JD 隔离

**日期**：2026-10-08

**做了什么**
简历改写的护栏从一道变成两道：代码检查通过后，再请模型逐条核对“改后新增的说法”能否在证据里找到出处。同时把用户粘贴的 JD 排除出证据，并让“主导、牵头、独立完成、独立负责”无论原文怎么写都必须有出处。

**为什么**
复查 v4 评测时发现：代码护栏报“编造 0”，但 LLM 评委给 57 条改写里的 11 条打了忠实 2 分（细则规定有编造最多 2 分）。逐条看，有真编造（用户说“没做过给药采血”，改写写了“小鼠给药”），也有语义抬高（“喜欢写作”→“文字功底扎实”，“写推文”→“独立完成选题、写稿、排版”）。代码只认数字、英文和固定词表，这些它看不见。“编造 0”这个核心指标比实际说得宽。

另一个漏洞是读代码发现的：用户贴进对话的 JD 被当成“用户说过的话”，JD 里的“熟练使用 SQL”就能作为出处写进简历。

**怎么做的**
| 改动 | 文件 |
|---|---|
| 事实核对：列出改后相对改前新增的动作、职责程度、能力判断、结果和渠道，逐条到证据里找出处；用户否认过的事最严重。同义改写、上位概括、证据别处有出处的不算问题。代码检查先跑，没过就不调模型；核对回复读不懂时放行，不让坏回复卡住用户 | `src/agent/claim-check.ts`（新） |
| JD 隔离：一段文字里出现两个不同的 JD 小标题（岗位职责、任职要求……）就当成 JD。附件整段去掉，打字粘贴的从第一个小标题那行截掉。证据统一由 `userEvidence` 生成，线上和评测同一口径 | `fabrication.ts`、`material-tools.ts` |
| 独占类说法（主导、牵头、独立完成、独立负责）始终要出处；“负责”仍只在原文是“参与/协助”时才拦，避免误报 | `fabrication.ts` |
| 评测新增指标：评委判为编造的条数、每场耗时；`--no-checker` 开关用来做对照实验 | `evals/run-resume-coach-sim.ts` |

**结果**
完整评测（9 个场景 × 2 次，`resume-coach-sim-v5-claim-check.json`）：

| 指标 | v4 | v5 |
|---|---|---|
| 评委判为编造（忠实 ≤ 2） | 11 / 57 | **2 / 57** |
| 评委忠实分 / 自然分 | 3.91 / 4.60 | 4.53 / 4.86 |
| 交付率 / 首次交付 | 100% / 第 1 轮 | 100% / 第 1 轮 |
| 素材挖出率 | 97% | 81% |
| 每场耗时 | 12.8 秒 | 15.3 秒 |

剩下 2 条里，一条的“约 120 只”其实是用户原话，评委误判，但同一条的“建立辐射损伤动物模型”是真抬高；另一条是“筹备”→“策划”，边界情况。

挖出率下降集中在 3 个场景，所以做了对照实验（同 3 个场景 × 4 次，只差有没有核对器）：

| 指标 | 无核对器 | 有核对器 |
|---|---|---|
| 评委判为编造 | 13 / 47 | 3 / 47 |
| 素材挖出率 | 88% | 81% |
| 每场耗时 | 12.9 秒 | 16.5 秒 |

编造减少约 77%，来自核对器；代价是挖出率可能低几个点（样本小，差 2 个素材点），每场多约 3.5 秒。漏掉的多是次要条目上的数字（microCT 扫描数量、宣传中心海报数量），推测是被退回的内容占用了“最多 4 个问题”的名额。

被退回的内容大多合理（“具备数据分析基础”“按类别归档，保证文件可随时调取”），也有误报：核对器把“配合校内活动输出图文物料”这类同义改写当成新增；代码把“5-6 名干事”判为编造（用户说的是“五六个”，中文数字是已知盲区）。

**学到的概念**
- **对照实验（ablation）**：一次改了几处，指标变了，不知道是哪处造成的。只关掉一处再跑，差值就是它的作用。
- **分层护栏**：便宜、确定的检查（代码）在前，贵、灵活的检查（模型）在后，前一层没过就不调后一层，省钱也省时间。
- **失败时放行还是拦截（fail open / fail closed）**：核对器回复读不懂时放行，因为前面已经有代码护栏兜底；如果它是唯一一道护栏，就应该拦截。
- **评委也会错**：评委说“120 只没有出处”，而用户原话就有。评委分数用来比较版本，具体结论要抽查原文。

**下一步**
- 挖出率：试着让被退回的内容不占提问名额，或者在提示词里规定问题优先问结果和规模，再用同一份考卷重测。
- 面试示范答案也接上事实核对（这次只做了 JD 隔离和独占词）。
- 专家意见卡片仍不过护栏（团队评测 15 场里标出 7 条可疑意见）。
