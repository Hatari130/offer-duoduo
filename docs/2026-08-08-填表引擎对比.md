# 填表引擎对比：Job-Application-Helper vs JobKoI

> 2026-08-08 · 聚焦「把资料填进招聘网站表单」这一能力
> 结论先行：**双方都有完整的填表引擎**，不是「对方有/我们没有」。差异在「检测哲学、站点适配策略、写入控件覆盖、AI 用法、校验强度」。

---

## 0. 总览

| 维度 | 对方（Job-Application-Helper） | 我们（JobKoI） |
|------|-------------------------------|-------------------|
| 检测入口 | `FormDetector.detectFields()` | `scanApplicationForm()` + `OfferFlowFormAdapters` |
| 匹配方式 | 通用相似度：**关键词 + Levenshtein >0.7**，confidence≥0.5 | **按 ATS 的数据驱动正则适配器**（北森/Moka/牛客/腾讯/generic） |
| 站点适配 | 字节系硬编码（`.ud__select` / `applyFormModuleWrapper`） | 4 个 ATS 适配器 + 用户可覆盖映射 |
| 写入核心 | `FormFiller.fillField()` | `setNativeValue()` |
| 控件覆盖 | 原生 input/select/textarea + 字节自定义 select + 简历上传 | 原生 + radio/checkbox + Element UI cascader/select + 字节/北森 phoenix-select（日期/地区/普通） |
| React 兼容 | 显式 `_valueTracker.setValue(oldValue)` + 直接调 react handler | 原生 setter + 派发 `input` 事件（标准 React onChange 触发路径） |
| 动态行 | `ensureRows` 自动点「添加」 | `ensureRepeatableEntries(repeatCounts)` 按传入计数展开 |
| 回读校验 | 仅 `element.value === value` 布尔 | `readControlValue` 回读 + `sendFillProgress` 实时进度 |
| AI 在填表里 | 字段分类 / 模块补填 / **视觉框选补填** / 开放题生成 | 仅未知字段**语义分类**（不发资料值） |

---

## 1. 字段检测 / 匹配

### 对方
- `FormDetector.detectFields()`：`querySelectorAll` 所有 `input/textarea/select`（排除 `hidden/submit/button`）。
- `FieldMatcher.extractIdentifiers` 抽 `name/id/placeholder/labelText/type/autocomplete`，向上找 `label[for]`、父 `label`、前序兄弟、`data-form-field-*`。
- `matchFieldType()`：**关键词 `includes` + Levenshtein 编辑距离 >0.7** 打分，`confidence >= 0.5` 才采纳；`email/tel/date/file` 直接定置信度 1.0。
- 偏「通用 + 字节硬编码」，对未知站点靠相似度兜底。

### 我方
- `OfferFlowFormAdapters.match(element, label, adapter)`：先用 `resolve()` 按 **hostname** 选适配器：
  - `beisen`（北森，含 `.phoenix-*`）、`moka`、`nowcoder`（牛客）、`tencent`（腾讯，含 CDN 域名 + 正文「腾讯招聘」兜底）、`generic`。
- 每个适配器 = `hosts` 正则 + `markers` DOM 信号 + `compiled` 正则映射（`commonMappings` 通用 + 该站专属 mappings）。
- 命中返回 `{ key, confidence: 0.96(站点)/0.86(generic), source:"rules" }`。
- **用户可覆盖**：`offerflow.formMappingOverrides` 存储自定义映射，运行时合并。
- 偏「数据驱动、按 ATS 分库」，比对方的「通用 + 字节」覆盖更多厂商，且可用户扩展。

> 差异点：对方用**算法相似度**应对任意站点；我方用**预置 ATS 规则库 + 用户覆盖**，对已知 ATS 更准更可控，对陌生站点靠 generic 正则兜底（无相似度打分）。

## 2. 写入机制（核心差异）

### 对方 `fillField()`
```
原生 setter 赋值
→ element._valueTracker.setValue(oldValue)   // 关键：骗过 React 的受控值追踪
→ triggerEvents(input/change/blur/keydown/keyup)
→ 直接调 element["__reactEventHandlers$..."].onChange(合成事件)  // 强制 React 接受
```
- `.ud__select`（字节自建下拉）：`mousedown`/`mouseup`/`click` + react handler 选 option。
- `uploadResume`：用 `DataTransfer` 设 `fileInput.files` 再 `triggerEvents`（**支持简历文件上传**）。

### 我方 `setNativeValue()`
```
原生 setter 赋值（HTMLInputElement/TextArea.prototype.value setter）
→ dispatchInputEvents(input/change)  // React 监听 input 事件触发 onChange
```
控件类型分支极广：
- 原生 `select`（option 文本/值匹配）
- `radio` / `checkbox`（HTML + `role=radio` + phoenix radio group）
- Element UI `cascader`（`.el-cascader` 级联选择）
- `role=combobox`（写值 + `ArrowDown`/`Enter`）
- `.el-select`（Element UI 下拉）
- `.phoenix-select`（北森）：**日期选择器、地区级联、普通下拉**各自专用路径
- `contenteditable`
- 默认 input/textarea

> 差异点：
> - 对方**显式操作 `_valueTracker`** + 直调 react handler，对 React 受控组件最稳；
> - 我方靠「原生 setter + 派发 input 事件」这条标准路径（React 16+ 的 onChange 本就绑定 input 事件，配合原生 setter即可触发），并对 **Element UI / 北森 phoenix 的级联、日期、地区控件**做了专门处理——这些是对方没有的深度适配。

---

## 3. 动态行 / 重复条目

- 对方：`prepareDynamicSections` → `ensureEducationRows`/`ensureExperienceRows` → `ensureRows`：按 `profile.education/experience.length` 自动点「添加」按钮补行；日期范围组件**先写结束时间再写开始时间**规避校验回滚。
- 我方：`ensureRepeatableEntries(message.repeatCounts)`：按 sidepanel 传入的 `repeatCounts` 展开重复条目。逻辑驱动方式不同（对方自驱于 profile 长度，我方由 UI 显式给计数）。

---

## 4. AI 在填表里的角色

| 用法 | 对方 | 我方 |
|------|------|------|
| 未知字段语义分类 | ✅ `MATCH_FIELDS_LLM` | ✅ `matchFormFields`（仅语义，不发资料值，conf≥0.65 才采纳） |
| 模块级空白补填 | ✅ `AI_FILL_SECTION` | ❌ |
| **视觉框选补填（截图+vison）** | ✅ `AI_FILL_VISUAL_REGION` | ❌ |
| **网申开放题生成** | ✅ `GENERATE_ANSWER` | ❌ |

- 双方共识：**AI 不编造**，只输出已存在的资料值。
- 差异：对方把 AI 用到了「补填 / 视觉 / 开放题」等边角场景，且支持 **OpenAI 兼容 + Claude** 双后端；我方 AI 在填表链路里只做「未知字段分类」，模型锁 DeepSeek。

---

## 5. 校验与反馈

- 对方：`fillField` 返回布尔（`element.value === value` 或选中文本匹配），汇总 `filledCount`。
- 我方：写后 `readControlValue(element)` **回读**做归一化比对，失败标记「写入后回读值不一致」；全程 `sendFillProgress` 推送 `started/field(n/total)/done`，sidepanel 实时显示进度。校验更闭环、可观测性更强。

---

## 6. 互为补充的亮点

- **可借鉴对方**：① 视觉框选补填（截图+vison 的「最后一公里」）；② 网申开放题生成；③ 显式 `_valueTracker` 重置以更稳妥兼容 React 受控组件；④ AI 后端可插拔（OpenAI 兼容/Claude）。
- **我方可输出给对方**：① 数据驱动的多 ATS 适配器 + 用户覆盖机制（比硬编码更好维护）；② Element UI / 北森 phoenix 的级联、日期、地区控件支持；③ 写后回读校验 + 实时进度反馈。
